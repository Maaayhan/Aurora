# Aurora —— 产品需求文档（中文版）

> 本文档是 [`docs/PRD.md`](../../PRD.md) 的中文翻译，仅用于学习，内容以英文原版为准。

## 1. 问题陈述

一个训练好的模型 checkpoint 本身不是一个产品。从"权重文件存在"到"用户能可靠地跟这个模型对话"之间，隔着一整套平台：得有东西去验证调用方身份、决定现在要不要接受这个请求、模型忙的时候把请求放进队列里排队、边生成边把 token 流式返回、知道什么时候该放弃并重试、知道什么时候该停止重试并大声报错而不是悄悄失败，还要把每个请求的足够信息记录下来，好让工程师在凌晨两点系统出问题的六小时后，还能复原出当时到底发生了什么。

Aurora 就是这套平台。它介于"Aurora AI 研究团队手上有一个 checkpoint"和"用户能发一条消息、并得到可靠响应"这两件事之间——不多不少，正好补上这段距离。

## 2. 目标

- 通过一个稳定的、有版本管理的 HTTP API，对外提供一个本地托管的开源 LLM 服务。
- 模型输出以 SSE 逐 token 流式返回，而不是一次性阻塞式返回。
- 把对话当作一等公民对象来追踪（会话、历史记录、时间戳），而不是无状态的一次性调用。
- 让每一种失败模式都是显式的、被处理过的：认证失败、限流、超时、推理错误、队列饱和、模型不可用。
- 让系统的内部状态可以从外部被观测到：日志、指标、链路追踪、健康检查——都不需要去读应用代码。
- 设计（不一定要完全实现）一条 checkpoint 发布流水线：一个新模型版本如何从"研究团队产出了它"安全地走到"正式承接生产流量"，并且有回滚路径。

## 3. 非目标

Aurora 刻意不包含：

- **任何业务领域逻辑。** 没有 CRM，没有病历系统，没有发票，没有针对特定客户的工作流。这里的任何东西都不是在为某个业务问题建模——而是在为一个"服务问题"建模。
- **RAG、Agent 或工具调用。** 这些是 AI *应用层* 关心的问题——它们运行在模型 API 之上，而不是运行在为模型提供服务的平台内部。如果把它们混进来，恰好会模糊掉这个项目存在的意义所要展示的那条边界。
- **模型训练或微调。** Aurora 消费一个 checkpoint，而不是生产一个 checkpoint。
- **打磨精致的聊天界面。** 一个极简客户端（curl 脚本 / 一个简陋的测试页面）就足以验证流式传输了。这是一个后端平台项目——工程价值不在 UI 上。
- **调用一个托管的第三方模型 API（OpenAI、Anthropic 等）作为真正的推理后端。** 应用代码只是把"兼容 OpenAI 的协议"当作一种线上数据格式来使用——真正回答请求的模型是在本地运行的。

## 4. 用户

只有一个外部参与者：**一个发送聊天请求、消费流式响应的客户端应用**。这里没有任何面向终端用户的产品决策需要做（没有引导流程、没有计费、没有多租户管理后台）——从设计决策的角度看，这个系统真正意义上的"用户"，是*未来要运维它、扩展它、或者在高负载下调试它的那个工程师*。

## 5. 分阶段范围

每个阶段的详细内容和完成标准都在 [`ROADMAP.md`](../../ROADMAP.md) 里。概览：

| 阶段 | 主题 | 要回答的问题 |
|---|---|---|
| 0 | 设计 | 系统的规格说明是否精确到"实现过程中不需要重新做决策"的程度？ |
| 1 | MVP | 客户端能不能发一条消息、可靠地流式收到响应，同时认证、限流、重试、日志都已就位？ |
| 2 | 生产加固 | 系统在并发压力下（排队、背压、熔断、取消、超时）能不能扛住，而不是直接倒下或者悄悄地把状态搞坏？ |
| 3 | 可观测性 | 运维人员能不能在不读源码的情况下，回答"这个系统现在在干什么"以及"某个具体请求为什么失败了"？ |
| 4 | 部署 | 有没有一条设计好的（哪怕不是完全自动化的）路径，能把"研究团队产出了 checkpoint-v17"变成"v17 正在承接生产流量"，并且带回滚？ |

## 6. 成功标准

对于作品集这个用途来说，Aurora 达到"完成"状态，需要满足：

1. 一个工程师只读 `docs/`（不看代码），就能对这个系统建立足够精确的认知，精确到自己动手实现也能做出跟真实实现很接近的结果。
2. Maincode 那份 JD 里点名提到的每一种可靠性机制——限流、重试、优雅失败、认证、流式传输、日志/遥测——都要真的存在于代码里，而不只是存在于文档里，并且能够按需演示"失败与恢复"（例如"看看我在流式传输过程中把推理容器杀掉会发生什么"）。
3. 这个系统能够被端到端地、口头地、从零开始讲清楚，讲述的方式要像一场真正的设计评审——不是背诵记忆，而是现场推理出来的，包括那些被否决掉的方案。

## 7. 明确的权衡取舍及理由

以下是评审者最有可能追问的几个决策点——提前把它们摆出来，而不是留着让人去猜：

- **选 Python/FastAPI，而不是作者更擅长的 NestJS/TypeScript。** 这是一个刻意*反着*作者最深生产经验语言去做的选择。有两个理由压过了这种本能：（1）真实的 LLM 服务生态——vLLM、TGI、Ray Serve、Triton，以及 Maincode 自己"Rust 推理引擎 + 上层 Python 服务层"的形态——绝大多数都是 Python 写的，所以用 Python 实现，看起来就像目标系统本来的样子，而不是把一个相邻技能横向搬过来；（2）这是诚实地去补一个真实存在、被点名提到的能力缺口，而不是绕开它——如果用一门作者本来就精通的 TypeScript 来做这个项目，会做出一个设计不错但什么都证明不了的东西。
- **本地开发只用 Ollama，不用 vLLM。** vLLM 的 PagedAttention/连续批处理引擎是面向 Linux + NVIDIA CUDA 的，在 macOS 上不能原生运行。Ollama 可以在 Apple Silicon 上通过 Metal 本地运行，并且暴露一个兼容 OpenAI 的 `/v1/chat/completions` 接口——这也是应用层被允许依赖的唯一契约。`VLLMProvider` 未来会针对真实 GPU 部署实现同一个接口——换 provider 只是一次配置修改，不是重写。这正是 `ARCHITECTURE.md` 第 4 节那条边界存在的意义。
- **选 Celery，而不是手写一个 asyncio 队列或者 `arq`。** Celery 是 Python 生态里成熟、开箱即用的选择——但它的默认配置是为"发完就不管"的后台任务调的，不是为"一个长时间运行、中途还要把部分输出实时流出去的任务"调的。有两个配置项（`task_acks_late`、`task_reject_on_worker_lost`）必须刻意打开，才能拿到相当于 BullMQ 那种崩溃安全性；这一点被当作一项明确点名的风险来对待，而不是一个想当然的假设——见 `ERROR_HANDLING.md` 第 6 节。
- **worker 是一个独立于 API 的进程**，通过 Celery + Redis pub/sub 连接，而不是让 API 在请求处理函数里直接调用模型。这么加是因为它能让"排队/限制并发"这个需求变得真实，而不只是摆设。理由见 `ARCHITECTURE.md` 第 3 节。
- **Ollama 跑在宿主机上，不跑在 Docker 里**，因为 macOS 上的 Docker Desktop 不会把 Metal 透传给 Linux 容器——把它容器化会让这个项目里所有的延迟数字都悄悄变得没有意义。见 `DEPLOYMENT.md` 第 1 节。
