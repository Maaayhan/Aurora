# Aurora —— 错误处理与失败模式（中文版）

> 本文档是 [`docs/ERROR_HANDLING.md`](../../ERROR_HANDLING.md) 的中文翻译，仅用于学习，内容以英文原版为准。

这里的每一行，都是一个系统被设计成"不需要运维人员介入就能扛过去"的场景。"扛过去"的意思是：给调用方返回一个清晰的、有类型的错误，记录足够用来排查问题的日志，并且让系统留在一个"下一个请求正常情况下应该能成功"的状态。

## 1. 限流

**算法**：滑动窗口日志（sliding window log），按 `identityId` 区分，存在 Redis 的有序集合里（`ratelimit:{identityId}`，分数是请求的时间戳）。每次请求：`ZREMRANGEBYSCORE` 删掉窗口外的旧记录，`ZCARD` 数一下还剩多少条，如果 `>= limit` 就拒绝，否则 `ZADD` 一条当前时间戳。

选这个算法而不是固定窗口计数器，是因为固定窗口会在窗口边界处放进来 `2 倍限额` 的突发流量（比如限额刚好卡在 23:59:59 用完，00:00:00 一到又能再用一次）——滑动窗口日志没有这个边界问题。选这个算法而不是令牌桶，是因为这里的需求是"每个窗口最多 N 次请求"，而不是"平滑吞吐量、允许一定突发"——令牌桶是解决"突发容忍度"问题的正确工具，但这里的需求恰好不是这个。

**超出限额时**：返回 `429`，错误码 `RATE_LIMITED`，`Retry-After` 头设置为距离窗口里最早那条记录过期还有多少秒。这个请求会在**碰到队列之前**就被拒绝——一个已经超额的客户端，不应该有任何机会给推理层增加负载。

## 2. 超时

有两个相互独立的超时，很容易被搞混，值得刻意区分开：

- **排队等待超时**（默认 60 秒）：如果一个任务在 Celery 队列里躺了超过这个时间还没有 worker 来捞它，就直接以 `SERVER_BUSY` 判定失败，而不是让它最终还是跑起来——一个在客户端已经放弃等待之后才姗姗来迟的响应，价值是负的；更好的做法是快速失败，让客户端在真的有容量的时候再重试。
- **推理超时**（默认 30 秒，按每次尝试计算）：一旦 worker 开始调用模型 provider，一个 `asyncio.wait_for` 的截止时间就会生效，如果在时限内没有数据到达，就会触发，取消底层的 `httpx` 请求。这是一个*按每次尝试*计算的超时，所以它会独立作用于每一次重试，而不是整个任务只算一次。

## 3. 重试策略

- 重试**只**适用于发生在"还没有任何 token 被流式传给客户端之前"的失败（原因见 `SEQUENCE_DIAGRAMS.md` 第 3 节）。一旦已经开始流式传输，后续任何失败对这个请求来说都是终态的——上报为一个 `error` SSE 事件，绝不重试。
- 指数退避：`0.5 秒 → 1 秒 → 2 秒`，总共最多 3 次尝试（1 次原始尝试 + 2 次重试），可以通过环境变量配置。
- 重试使用 Celery 原生的 `autoretry_for` / `self.retry(countdown=...)` 机制，而不是手写一个循环——结合 `task_acks_late=True`（见第 6 节），这意味着重试状态能扛过两次尝试之间发生的 worker 崩溃（这个任务只会被另一个 worker 捞起来，Celery 自己的重试计数器保持完好）。
- 每一次重试都会用同一个 `request_id` 记录日志，并附带一个递增的 `retry_count`，这样 Postgres 里 `messages.retry_count`（见 `DATA_MODEL.md`）反映的就是一次响应的真实成本，而不只是它最终的延迟数字。

## 4. 熔断器

每个 worker 各自维护一份内存中的状态，同时镜像一份到 Redis 的 `circuit:inference` 里，这样所有 worker 副本就能收敛到同一个视图，而不需要每一个都各自独立地重新发现"模型现在挂了"这件事。

- **关闭（Closed，正常状态）**：请求自由通行，失败次数在一个滑动时间窗口里累计计数。
- **打开（Open）**：当失败次数超过阈值时触发（默认：30 秒内失败 5 次）——在冷却期内（默认 20 秒），完全跳过对 Ollama 的调用；worker 立刻以 `INFERENCE_UNAVAILABLE` 判定任务失败。这就是那个能阻止"一个正在挣扎的模型被一波又一波重试请求继续猛砸"的机制。
- **半开（Half-open）**：冷却期结束后，放下一个单独的请求通过，作为探测。成功 → 恢复关闭状态（计数器清零）。失败 → 重新打开，冷却期重新开始计时。

这是规范里"模型反复失败 → 后端停止发送请求，防止级联失败"这条要求的直接实现。

## 5. 背压（Backpressure）

队列深度会在请求发生的那一刻、入队之前，同步检查一次（见 `SEQUENCE_DIAGRAMS.md` 第 4 节）。阈值是一个可配置的最大队列长度（默认 200，可以根据观察到的 worker 吞吐量调整）。超过阈值 → 立刻返回 `503 SERVER_BUSY`，完全不尝试入队。这正是防止"队列变长了"演变成"队列无限增长、背后的 Redis 实例被 OOM 杀掉"的机制——失败被推回到了边缘（直接拒绝请求），而不是被内部悄悄吸收，最终以一种更严重的失败形式冒出来。

## 6. Worker 在任务执行中途崩溃

Celery 的默认行为是：在 worker *接收到*任务的那一刻就确认（ack）并丢弃它的记录，而不是等它真正执行完才确认——一个在推理过程中崩溃的 worker，会悄悄弄丢这个任务，且没有任何重试。这个默认行为被显式关掉了：Celery 配置里设置 `task_acks_late=True` + `task_reject_on_worker_lost=True`，这样一个任务只有在成功或者显式失败时才会被确认，而一个在执行过程中所属 worker 消失了的任务，会被放回队列，交给另一个 worker 去捞。之所以要特意把这一点讲出来，是因为它*不是*默认行为——一个从来没设置过这两个开关的 Celery 部署，看起来跟设置过的部署一模一样，直到某次生产环境里一个 worker 崩溃、任务无声无息地消失，才会露出马脚。如果崩溃发生在 token 已经开始流向客户端之后，那个客户端的 SSE 连接也会跟着断掉（发布消息的那个 worker 已经没了）——客户端看到的是一个关闭的连接、没有任何 `done`/`error` 事件，根据 `API_SPEC.md` 的规定，这种情况要被明确当作"传输层失败，可以安全地整体重试这个请求"来处理。（被重新入队的这个任务本身，仍然受第 3 节"部分输出之后不能重试"这条规则约束——但从*新*worker 的视角看，这是一次全新的、还没发出过任何 token 的尝试，所以重试它是安全的；只有从"一个 worker 重试自己已经在流式输出的那次尝试"的视角看，它才是不安全的。）

## 7. 依赖服务中断

| 哪个依赖挂了 | 影响 | `/health` 上报的状态 |
|---|---|---|
| Postgres 不可达 | 网关无法给新会话做认证，也无法持久化消息——**硬性失败**，除健康检查接口外，所有接口都返回 `5xx` | `status: unhealthy` |
| Redis 不可达 | 限流、排队、流式传输全部失效——**硬性失败**（根据 `DATA_MODEL.md` 第 4 节，Redis 是承重的，不是可有可无的缓存） | `status: unhealthy` |
| Ollama 不可达 | 已有的对话/历史记录仍然可以正常读取；新的推理请求会在熔断器触发之后快速失败 | `status: degraded` |

Postgres/Redis 挂掉这两种情况，被刻意地**不**当作"优雅降级"来处理——当系统连认证和状态追踪都做不到的时候，不存在任何安全的"部分可用"模式，假装还能提供部分功能（比如悄悄地用陈旧的缓存认证结果继续服务）会比诚实地返回一个 503 更糟糕。

## 8. 畸形或者恶意的输入

- 请求体在路由边界通过 Pydantic 模型校验（FastAPI 会在处理函数体真正执行之前，拒绝任何不符合 schema 的请求）——以 `400 INVALID_REQUEST` 拒绝，这样就不会有任何一个"只校验了一半"的请求进入队列。
- 消息长度上限为 4000 字符，同时限制了队列载荷的大小和发给模型的 prompt 长度。
- 模型 provider 返回的内容始终被当作不透明的 token 文本，原样流式传递（任何地方都不会对模型输出做 `eval`，也不会做模板插值）——唯一一个这条原则会真正起作用的地方（如果 Aurora 未来真的把模型输出渲染成 HTML）目前明确超出范围，因为现在没有 UI；但这个原则在这里被记录下来，以防将来真的构建一个客户端时被遗忘。

## 9. "优雅失败"明确不包括什么

这一点值得说清楚，因为"优雅"这个词很容易被过度解读：Aurora 不会尝试悄悄换成另一个模型来顶替、不会在推理失败时编造一个看起来说得通的响应、也不会无限重试、指望它总有一次能成功。上面列出的每一种失败模式，最终都只会走向两种结果之一——"成功"，或者"一个调用方可以据此采取行动的、有类型的错误"——绝不会是一个"看起来像成功、但背后其实没有一次真实模型补全支撑"的响应。
