# Aurora — Roadmap

No fixed calendar dates. A Maincode take-home, if it comes, will land on its own schedule — this roadmap is ordered by dependency and risk, not by week number, so it stays useful whether the next work session is tomorrow or in a month.

Each phase has a **definition of done** — a concrete thing that must be demonstrable, not just "code exists."

## Phase 0 — Design (done)

**Done when**: every doc in `docs/` exists, is internally consistent (no contradiction between `ARCHITECTURE.md` and `SEQUENCE_DIAGRAMS.md`, etc.), and can be explained out loud from a cold start without re-deriving the reasoning live. Repo skeleton exists (`app/`, `worker/`, `providers/`, `shared/`, `docker/`, `scripts/`) even though the directories are empty.

**Explicitly not done in this phase**: any application code. Writing code before the queue/streaming bridge design (`ARCHITECTURE.md` §5) was nailed down would have meant either building the naive "API calls the model provider directly" version and reworking it later, or discovering the process-boundary streaming problem mid-implementation under time pressure. Designing it first is cheaper.

## Phase 1 — MVP

**Done when**: a client can `POST /chat`, authenticate with either a JWT or API key, get a token-by-token SSE stream back, have it persisted as a conversation, get rate-limited with a proper `429` past a threshold, see a failed inference call retried with backoff, and have every request show up as a structured JSON log line with `request_id`, latency, and status. `/health` reports real status for Postgres/Redis/Celery/Ollama, not a hardcoded `200 OK`.

Scope: `app/core/auth.py`, `app/core/rate_limit.py`, `app/api/chat.py`, `app/services/session_service.py` (API side) + a minimal `worker/tasks.py` with the queue/pub-sub bridge from `ARCHITECTURE.md` §5 already in place, and `providers/ollama_provider.py` as the first `ModelProvider` implementation — the API/worker split is not deferred to Phase 2, because retrofitting it after the fact is exactly the rework Phase 0 exists to avoid. Retry-with-backoff (no circuit breaker yet) and basic structured logging (`structlog`) land here too, straight off `ERROR_HANDLING.md` §3. `task_acks_late=True` / `task_reject_on_worker_lost=True` are set from the first Celery config, not added later — see `ARCHITECTURE.md` §2.

Minimum 7 Prometheus metrics exposed (even if Grafana isn't wired up until Phase 3): `aurora_requests_total{status}`, `aurora_request_duration_seconds` (histogram), `aurora_rate_limit_rejections_total`, `aurora_inference_errors_total{code}`, `aurora_queue_depth`, `aurora_ttft_seconds` (time to first token — histogram), `aurora_tpot_seconds` (time per output token — histogram). TTFT/TPOT are the two metrics that make this look like real inference-serving observability rather than generic API metrics with a chat endpoint bolted on.

## Phase 2 — Production hardening

**Done when**: the failure modes in `ERROR_HANDLING.md` can each be triggered on demand and observed behaving as documented — kill the Ollama process mid-stream and watch the client get a clean `error` event, not a hang; fire 50 concurrent requests at a worker capped at `--concurrency=8` and watch the rest queue instead of falling over; close a client connection mid-stream and confirm (via logs) the worker actually stopped generating instead of wasting compute on an abandoned request; kill a worker process mid-task and confirm (via Flower) the task gets picked up by another worker instead of silently vanishing.

Scope: circuit breaker (`ERROR_HANDLING.md` §4), backpressure rejection at the API (§5), cooperative cancellation propagation (`SEQUENCE_DIAGRAMS.md` §2), per-attempt vs. per-task timeout distinction (§2). This phase is where the project stops being "a chat API with a queue" and becomes a system that has been deliberately made hard to break — which is the literal sentence the JD uses to describe what the role wants.

## Phase 3 — Observability

**Done when**: given only a `request_id`, an operator can find the full path of that request (API → queue wait → worker → model provider call → response) via a Jaeger trace, without reading application code or grepping raw logs. Grafana dashboard shows live request rate, p50/p95 latency, error rate by code, queue depth, and TTFT/TPOT distributions, refreshing against real traffic generated by a load-test script (`k6`). Flower shows live worker/task state as a complementary, zero-setup view alongside the Prometheus/Grafana stack.

Scope: OpenTelemetry instrumentation across the API→queue→worker boundary (the exact boundary that makes this system's tracing non-trivial — a request literally changes process partway through, which is the interesting case to demonstrate, not a single-process trace), Jaeger collector, Grafana dashboard provisioned as code (not clicked together by hand, so it's reproducible).

## Phase 4 — Deployment

**Done when**: `scripts/deploy.py checkpoint-v17` runs the register → warm-up → smoke-test sequence from `DEPLOYMENT.md` §2 against a locally-tagged Ollama model standing in for a new checkpoint, and a corresponding `scripts/rollback.py` reverts traffic without redeploying. Canary weighting and automated rollback triggers (§2 steps 4–5) are implemented if time allows; if not, they remain fully specified in `DEPLOYMENT.md` and that's an honest, defensible place to stop — "designed but not automated" is a normal, real answer for a feature this deep into a serving platform's maturity curve.

## Bonus scope (only after Phase 1–2 are solid, never instead of them)

Multi-model routing, model versioning, A/B testing, shadow deployment, token-usage/cost accounting — all listed in the original spec, all made possible without rework by the `ModelProvider` boundary (`ARCHITECTURE.md` §4) and the `model` field already present in the task payload (`DATA_MODEL.md` §3) and `model_deployments` table (§1). Deliberately not scheduled into a numbered phase — these are what "if there's time" looks like, and pulling them earlier than Phase 2 being done would mean impressive-sounding bonus features sitting on top of a platform that hasn't actually proven it doesn't fall over under load, which is backwards.

## Non-negotiable ordering rule

Phase 2 does not start until Phase 1's definition of done is real and demonstrable, not "basically there." A serving platform with streaming and auth but no tested failure handling is a demo; the entire premise of this project (see `README.md`) is not building a demo.
